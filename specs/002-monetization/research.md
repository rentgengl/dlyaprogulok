# Research: Монетизация (002)

Фаза 0 плана. Каждый пункт: решение → обоснование → отвергнутые варианты. Неясностей
(NEEDS CLARIFICATION) после этой фазы не осталось; вопросы к бухгалтеру/юристу вынесены в
конец отдельно — они не блокируют разработку и тестирование на тестовом магазине.

## R1. Учёт баллов: журнал с двойной записью в SQLite

**Decision**: таблица `ledger_entries` — неизменяемые проводки; каждая операция
(`ledger_tx`) состоит из ≥ 2 проводок с суммой 0 по счетам. Счета — строки:
`user:<id>` и системные `sys:yookassa` (деньги, пришедшие через ЮKassa), `sys:revenue`
(выручка сервиса: траты на генерацию и комиссии), `sys:payouts` (выплачено пользователям),
`sys:refunds` (возвраты платежей). Текущий остаток пользователя хранится в `wallets.balance`
и меняется только в той же транзакции SQLite, что и проводки.

**Rationale**: FR-029 и SC-003 требуют, чтобы остатки сходились с журналом, а журнал — с
ЮKassa. Двойная запись даёт проверку одной SQL-строкой (`SUM(amount) = 0` по каждой
операции и `wallets.balance = SUM(amount)` по счёту пользователя) и сводку выручки для
админки без отдельных отчётов. Сервер один и работает с SQLite синхронно (`node:sqlite`),
поэтому `BEGIN IMMEDIATE … COMMIT` исключает гонки без блокировок на уровне приложения.

**Alternatives considered**: только `users.balance` без журнала — не проверяется и не
объясняет пользователю историю; одиночная запись без системных счетов — нельзя сверить
выручку и деньги ЮKassa; внешняя биллинговая система — избыточно для одного сервера и
противоречит принципу VIII (новые зависимости только при необходимости).

## R2. Резервы и заморозки

**Decision**: таблица `holds` (`kind`: `charge` для генерации, `payout` для заявки на
вывод; `status`: `active` → `captured` | `released`). Доступно = `balance − SUM(active
holds)`. Резерв ставится при запуске платного действия на сумму показанной пользователю
цены; по мере готовности результата из резерва списывается фактическая стоимость
(проводка `user → sys:revenue`), остаток резерва снимается при завершении задачи.

**Rationale**: FR-007 (списание не больше оценки), FR-009 (резерв → списание за результат),
FR-011 (не уходить в минус при параллельных действиях) и FR-024 (заморозка по заявке).
Резерв не двигает деньги, поэтому отмена — просто смена статуса без обратных проводок.
Фоновая задача после перезапуска сервера видит свой резерв по `job_id` и не ставит новый —
это закрывает edge case «списание не повторяется при продолжении».

**Alternatives considered**: списывать сразу и возвращать при ошибке — лишние проводки и
мигающий баланс; блокировать «на всё время задачи» без частичного списания — пользователь
переплачивает за точки, где рассказ не создался.

## R3. Деньги в целых единицах

**Decision**: баллы — `INTEGER`; рубли в платежах — `INTEGER` копеек. 1 балл = 100 копеек.
Доля автора с продажи/премии = `floor(price × (100 − pct) / 100)`, комиссия — остаток.
К выплате по заявке = `floor(points × 100 × (100 − pct) / 100)` копеек.

**Rationale**: исключает ошибки плавающей точки; правило округления зафиксировано в спеке.

## R4. Интеграция с ЮKassa без SDK

**Decision**: модуль `server/src/payments.ts` с интерфейсом `PaymentGateway`
(`createPayment`, `getPayment`, `createRefund`) и двумя реализациями: `yookassa` (HTTP API
v3 через `fetch`, Basic-auth `shopId:secretKey`, заголовок `Idempotence-Key`) и `fake`
(в памяти, для тестов и разработки — по образцу `MAIL_TRANSPORT=log`). Платёж создаётся с
`capture: true`, `confirmation: { type: 'redirect', return_url }`, `metadata.payment_id`
(наш id) и чеком `receipt`.

**Rationale**: официальный Node SDK ЮKassa не нужен — используются три вызова; `fetch`
встроен в Node 24. Интерфейс позволяет тестировать весь денежный путь без сети, как уже
сделано для почты, ИИ и озвучки.

**Alternatives considered**: npm-пакеты-обёртки над API ЮKassa — неофициальные, лишняя
зависимость; виджет ЮKassa встраиваемый в страницу — не работает в нативном приложении,
а redirect одинаково работает в вебе и Android.

## R5. Подтверждение оплаты: уведомление + сверка

**Decision**: `POST /api/payments/yookassa/notify` принимает HTTP-уведомления ЮKassa
(`payment.succeeded`, `payment.canceled`, `refund.succeeded`), но **не доверяет телу**:
по `object.id` сервер запрашивает платёж у ЮKassa (`GET /v3/payments/{id}`) и применяет его
фактический статус. Дополнительно — проверка IP отправителя по опубликованному ЮKassa списку
диапазонов (настройка, по умолчанию включена в production). Начисление баллов идемпотентно:
переход `pending → succeeded` выполняется условным `UPDATE … WHERE status = 'pending'`
в одной транзакции с проводкой. Клиент после возврата со страницы оплаты опрашивает
`GET /api/payments/:id`, который при статусе `pending` сам сверяется с ЮKassa (раз в 5 с).
Фоновая сверка раз в 10 минут проверяет «зависшие» `pending`-платежи моложе 24 часов.

**Rationale**: уведомления ЮKassa не подписаны — запрос статуса из API единственный надёжный
источник. Опрос при возврате даёт SC-001 (зачисление < 2 мин) даже без уведомлений (например,
локально). Условный `UPDATE` закрывает edge case с двойным уведомлением.

**Alternatives considered**: доверять телу уведомления — подделка начисляет баллы; только
опрос без уведомлений — пользователь, закрывший окно, не увидит баллы до следующего входа.

## R6. Кассовый чек (54-ФЗ)

**Decision**: в каждом платеже передаётся `receipt`: `customer.email` пользователя, одна
позиция «Баллы сервиса «Для прогулок», N шт.», `quantity: 1`, сумма платежа,
`vat_code` и `tax_system_code` — из настроек, `payment_mode: 'full_prepayment'`,
`payment_subject: 'service'` (значения по умолчанию, меняются в настройках без релиза).
При возврате передаётся чек возврата с той же позицией.

**Rationale**: «Чеки от ЮKassa» формируют чек сами по данным `receipt`; хранить фискальные
данные у себя не нужно. Признаки способа и предмета расчёта зависят от учётной политики
владельца, поэтому вынесены в настройки.

**Alternatives considered**: `payment_mode: 'advance'` / `payment_subject: 'payment'`
(аванс без указания услуги) — тоже допустимы; выбор подтверждает бухгалтер (см. вопросы).

## R7. Возврат с оплаты в приложение

**Decision**: веб — `location.assign(confirmation_url)`, `return_url =
${APP_URL}/wallet?payment=<id>`. Android — `Linking.openURL(confirmation_url)` в системном
браузере, `return_url` — та же веб-страница, которая предлагает вернуться в приложение по
ссылке `rasskazhi://wallet?payment=<id>`; при возвращении приложения на передний план экран
«Баллы» опрашивает `GET /api/payments/:id`. iOS — кнопка покупки баллов не показывается
(`Platform.OS === 'ios'`), остальные платные функции работают.

**Rationale**: без новых зависимостей (`expo-linking` уже есть, `scheme: rasskazhi` задан);
статус всё равно приходит с сервера, поэтому неважно, как пользователь вернулся.

**Alternatives considered**: `expo-web-browser` (`openAuthSessionAsync`) — удобнее, но новая
зависимость; можно добавить позже. Встроенные покупки Apple на iOS — отдельная функция.

## R8. Цена генерации и бесплатный лимит

**Decision**:
- Маршрут: `ceil(minutes / 180) × PRICE_ROUTE`, где `minutes` — из запроса (`durationMin`)
  или оценка `estimateDurationMin(distanceM)` для маршрута по длине; цена фиксируется при
  запуске (то, что увидел пользователь).
- Рассказ: `PRICE_STORY` за точку. Озвучка: `ceil(seconds / 120) × PRICE_NARRATION`.
  Оценка до запуска — по длине текста (по умолчанию 14 символов/с; настраивается), факт —
  по длительности mp3 (подсчёт MPEG-кадров в `tts.ts`, без зависимостей). Списывается
  `min(факт, оценка)`.
- Заказ «рассказы для маршрута» до запуска показывает сумму по всем точкам: рассказ +
  оценка озвучки при средней длине рассказа (настройка, по умолчанию 1 200 символов).
- Бесплатный маршрут (в пределах месячного лимита): задача подбора помечается
  `billing: 'free'`, и рассказы с озвучкой, которые она ставит автоматически, тоже
  бесплатны. Все следующие задачи и запросы по маршруту — платные.
- Платный маршрут (сверх лимита): автоматические рассказы **не** ставятся вместе с подбором;
  после создания маршрута пользователь видит точную цену рассказов (число точек известно)
  и подтверждает её отдельно.
- Ручной маршрут (без подбора) по-прежнему бесплатен и не тратит лимит; рассказы и озвучка
  для его точек — платные.
- Готовый рассказ, взятый из другого маршрута, стоит так же, как новый (пользователь платит
  за результат, спека — Assumptions).

**Rationale**: FR-005…FR-008a. Отказ от автоматических рассказов при платном подборе
позволяет показать точную цену (FR-007) вместо грубой оценки по неизвестному числу точек.

**Alternatives considered**: оценивать рассказы по максимальному числу точек и резервировать
с запасом — пользователь видит завышенную цену и «замороженные» баллы.

## R9. Подтверждение цены клиентом

**Decision**: каждый платный запрос передаёт `expectedCost` — сумму, которую пользователь
увидел и подтвердил. Сервер пересчитывает цену; если она выше `expectedCost` — `409
PRICE_CHANGED` с новой ценой, ничего не списывая. Цены получаются из
`GET /api/pricing` и из полей `quote` в ответах о маршруте.

**Rationale**: SC-002 «ни одно списание не превышает показанную сумму» гарантирует сервер,
а не интерфейс (принцип VI). Закрывает гонку «администратор поменял цену, пока
пользователь смотрел на экран».

## R10. Закрытие содержимого платного маршрута

**Decision**:
1. `fullRoute()` для зрителя без доступа возвращает превью: `summary` + цена, статус,
   обложка (первое фото точки), число точек; **без** `points`, `geometry`, финиша.
   Точка старта остаётся (нужна каталогу для фильтра «Рядом» и карты города) — спека
   FR-013 уточнена.
2. `GET /api/routes/:id/export`, `/suggestions`, рейтинг, премия «по маршруту» для чужого
   закрытого маршрута — проверка доступа через общую функцию `canView(route, user)`.
3. Файлы `/media/*`: статическая раздача заменяется обработчиком, который для файлов
   платных маршрутов требует подпись `?sig=<hmac>&exp=<unix>`; подписанные ссылки выдаются
   в `fullRoute()` только тем, у кого есть доступ, на 12 часов. Файлы бесплатных маршрутов
   раздаются как раньше. Ключ подписи — `MEDIA_SIGNING_KEY` (генерируется и сохраняется в
   настройках при первом запуске, если не задан).
4. `findSharedStory()` и копирование чужой озвучки исключают точки платных маршрутов —
   иначе их рассказы бесплатно попадали бы в чужие маршруты.
5. Превью для мессенджеров (`/route/:id`) — только название, описание, факты, обложка.

**Rationale**: SC-005 требует закрыть все пути доступа. `<audio src>` и `<img>` не передают
заголовок авторизации, поэтому нужны подписанные ссылки.

**Alternatives considered**: переименовывать файлы при продаже — не отзывает уже
выданные ссылки; отдавать медиа только через авторизованный `fetch` в `blob:` — ломает
потоковое воспроизведение длинной озвучки на мобильных.

## R11. Удаление маршрутов и аккаунтов с покупателями

**Decision**:
- Маршрут, у которого есть покупатели, при удалении автором не удаляется, а помечается
  `deleted_at`: исчезает у автора и из каталога, остаётся у покупателей (FR-014).
- Аккаунт автора, у которого есть проданные маршруты, при удалении обезличивается:
  `deleted_at`, адрес и имя заменяются («Удалённый автор»), сессии и пароль сбрасываются,
  маршруты без покупателей и медиа к ним удаляются. Без проданных маршрутов — удаляется
  полностью, как сейчас.
- Журнал ссылается на пользователя строкой `user:<id>` без внешнего ключа и не удаляется
  никогда (учёт, FR-029).

**Rationale**: каскадное удаление (`ON DELETE CASCADE`) уничтожило бы купленный доступ и
историю денег.

## R12. Проверка платных маршрутов

**Decision**: колонки маршрута `price`, `sale_status` (`pending` | `approved` | `rejected` |
`delisted`), `sale_note`, `sale_decided_at`, `sale_decided_by`. Каталог показывает маршрут,
если `is_public = 1` и (`price IS NULL` или `sale_status = 'approved'`). Отклонение:
`is_public = 0`, `price = NULL`, причина сохраняется в `sale_note` и письме. Снятие с продажи
(`delisted`) скрывает маршрут из каталога, покупатели сохраняют доступ. Повторная заявка
после отклонения разрешена.

## R13. Блокировки и права

**Decision**: заблокированный пользователь не может тратить баллы и подавать заявки (его
счёт «заморожен» — FR-025); входящие продажи и премии продолжают зачисляться. Все платные
действия требуют подтверждённой почты (`requireVerified`, FR-032). Ограничение частоты:
покупка баллов — 10/час, заявки на вывод — 5/сутки, премии — 30/час.

## R14. Документы

**Decision**: оферта — новый экран `/offer` (тот же `LegalPage`), ссылка на неё — на экране
покупки баллов и в «Условиях»; политика — новый раздел о ЮKassa. Тексты готовит разработка
по требованиям FR-031, юридическую выверку делает владелец.

## Вопросы владельцу, бухгалтеру и юристу (не блокируют разработку)

1. Система налогообложения и НДС для `tax_system_code` / `vat_code` (по умолчанию: УСН
   «доходы», без НДС).
2. Признаки расчёта в чеке: `full_prepayment` + `service` или `advance` + `payment`.
3. Текст оферты, особенно: вывод купленных баллов, комиссия 5 %, отсутствие возврата за
   открытые маршруты, ответственность авторов за налоги.
4. Риск по 115-ФЗ (вывод купленных баллов) — принят владельцем; нужна ли дополнительная
   проверка при выводе крупных сумм.
