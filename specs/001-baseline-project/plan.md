# План и архитектурный baseline проекта Rasskazhi

**Статус:** черновик на основе архива. Документ описывает текущую архитектуру и рекомендуемые правила её изменения.

## 1. Технологический стек, обнаруженный в архиве

| Область | Текущее решение |
|---|---|
| Клиент | Expo SDK 58, React Native 0.88, React 19, TypeScript 6 |
| Навигация | Expo Router |
| Web | React Native Web |
| Сервер | Node.js >=24, Fastify 5, TypeScript |
| Хранилище данных | SQLite (`node:sqlite`), WAL |
| Валидация | Zod |
| Аутентификация | Парольный хэш scrypt, сессионные токены |
| ИИ | Claude / DeepSeek через общий интерфейс |
| Геоданные | OpenStreetMap, Overpass, Nominatim, OSRM |
| Энциклопедические данные | Wikipedia, Wikidata |
| Фото | Wikimedia Commons |
| TTS | Yandex SpeechKit или OpenAI-совместимый API, локальный Piper |
| Карта | Leaflet; мобильная/веб-обвязка в клиенте |
| Почта | Nodemailer / SMTP |
| Контейнер TTS | Docker Compose |

Версии приведены по package manifests архива и могут измениться в рабочей ветке.

## 4. Границы ответственности

### Клиент
- Отображает пользовательские сценарии и состояние API.
- Использует Expo Router для навигации.
- Содержит общие API-клиенты, типы, авторизацию и платформенные реализации хранения/сохранения файлов.
- Не должен самостоятельно определять права доступа, месячные лимиты или окончательную геометрию маршрута.

### HTTP-слой (`server/src/app.ts`)
- Валидирует входные данные.
- Проверяет сессию, пользователя и права доступа.
- Оркестрирует доменные модули, БД и фоновые задачи.
- Формирует HTTP-ответы и ошибки.
- Не следует переносить сложные алгоритмы маршрутизации или промпты непосредственно в обработчики.

### Планировщик и геометрия
- `planner.ts` отвечает за выбор и отбор точек и подгонку маршрута под бюджет.
- `geo.ts` содержит расчёты расстояний, длины, порядка остановок и бюджета.
- Геометрия и ограничения должны оставаться детерминированными и тестируемыми.

### Внешние сервисы
- `services.ts` отвечает за получение кандидатов, статей, геокодирование и пешеходную маршрутизацию.
- `places.ts` обогащает места данными Wikidata, Commons и сведениями о культурном наследии.
- `ai-provider.ts` выбирает провайдера, `ai.ts` определяет общий контракт и промпты, адаптеры реализуют конкретные API.
- `tts.ts` скрывает различия провайдеров озвучки.

### Данные
- `db.ts` — источник схемы SQLite и миграций.
- Файлы загружаемых материалов хранятся на локальном диске в текущей реализации.
- Настройки, сохранённые администратором в БД, могут переопределять значения окружения, кроме ряда инфраструктурных параметров.

## 5. Основные потоки данных

### Генерация маршрута
1. Клиент отправляет запрос на генерацию.
2. Сервер проверяет пользователя, подтверждение почты (если включён SMTP), лимиты и параметры.
3. Источники находят кандидатов вокруг старта.
4. Кандидаты нормализуются и объединяются.
5. ИИ выбирает идентификаторы кандидатов либо используется эвристика.
6. Сервер проверяет выбранные идентификаторы.
7. Планировщик определяет порядок и подгоняет маршрут под целевой бюджет.
8. Маршрут и точки сохраняются в SQLite.
9. При асинхронном сценарии клиент опрашивает состояние фоновой задачи.

### Создание рассказа
1. Сервер определяет источник сведений для места.
2. Выбирает стиль `facts` или `legends`.
3. Вызывает ИИ при наличии провайдера.
4. При необходимости использует резервный текст.
5. Сохраняет рассказ, источник и версию формата.
6. При доступной озвучке создаёт MP3 и сохраняет медиа с признаком narration и голосом.

### Редактирование точки
1. Сервер проверяет владельца маршрута.
2. Проверяет лимит точек, расстояние и валидность координат.
3. Перестраивает порядок/геометрию маршрута.
4. Сохраняет согласованные данные в БД.

- Внутренние HTTP-маршруты перечислены в `contracts/api-contract.md`.
- Структуры БД — в `contracts/database-contract.md`.
- Внешние сервисы — в `contracts/integrations-contract.md`.
- Для точных схем запросов/ответов при изменении API необходимо сверяться с Zod-схемами и обработчиками в `server/src/app.ts`, а также клиентскими типами `app/src/lib/types.ts`. Этот baseline не подменяет исходный код как источник точной схемы.

## 8. Тестирование и проверки

В архиве присутствуют:
- `server/test/api.test.ts`
- `server/test/features.test.ts`
- `server/test/jobs.test.ts`
- `server/test/admin.test.ts`

Скрипты:
- корень: `npm test`, `npm run typecheck`;
- сервер: `npm test`, `npm run typecheck`;
- приложение: `npm run typecheck`, `npm run lint`.

Перед завершением изменений:
1. Запустить релевантные тесты.
2. Запустить корневой `npm run typecheck`.
3. Для клиентских изменений запустить `npm --prefix app run lint`.
4. Проверить миграции на копии БД, а не на единственной production-базе.

## 9. Архитектурные ограничения и технический долг

Подтверждено README:
- Публичные OSM/Overpass/Nominatim/OSRM сервисы не рассчитаны на произвольную production-нагрузку.
- Локальное файловое хранилище требует замены/абстракции при горизонтальном масштабировании.
- Для production требуется HTTPS за reverse proxy.
- Необходимо внедрить модерацию и жалобы для публичного контента.
- Требуется проверить соответствие политики конфиденциальности фактической передаче данных внешним AI-провайдерам.

Не подтверждено архивом как реализованное:
- централизованная наблюдаемость, метрики и трассировка;
- автоматическое резервное копирование и проверенное восстановление;
- CI/CD pipeline и release automation;
- объектное хранилище и multi-instance deployment.

## 10. Конституционные проверки (Constitution Check)

Перед реализацией:
- Не нарушается ли мобильная кроссплатформенность?
- Сохраняется ли проверка реальности геообъектов?
- Остаётся ли геометрия и бюджет маршрута на стороне детерминированного кода?
- Валидируются ли ответы ИИ и пользовательский ввод?
- Сохраняются ли авторизация, приватность и права доступа?
- Учтены ли лицензии и атрибуция стороннего контента?
- Есть ли тесты и безопасная миграция данных?
- Документированы ли внешние зависимости и fallback?

Если ответ отрицательный, план должен объяснить исключение и компенсирующие меры.
