# Конституция проекта «Для прогулок» (Rasskazhi)

## Core Principles

### I. Пользовательская ценность и мобильный приоритет

Продукт — создание и прохождение пеших онлайн-экскурсий на iOS, Android и Web. Каждое
изменение MUST улучшать или сохранять путь пользователя: выбор города и старта → маршрут →
прогулка и рассказы → обмен экскурсией.

- Основные сценарии MUST оставаться доступными на всех поддерживаемых платформах.
- Интерфейс MUST быть удобен на прогулке: читаемый текст, крупные элементы управления,
  явные состояния загрузки, пустого результата и ошибки.
- Веб-версия MUST сохранять функциональную совместимость там, где функция предусмотрена
  продуктом; платформенные отличия документируются в спецификации функции.

**Обоснование:** приложением пользуются на ходу, с телефона и при нестабильной связи.

### II. Достоверность геоданных и маршрутов

Маршруты строятся только по реальным объектам и реальной пешеходной сети.

- ИИ MUST выбирать только из объектов, полученных из проверяемых источников; сервер MUST
  проверять идентификаторы выбранных объектов.
- Порядок остановок, длина маршрута и соблюдение бюджета прогулки MUST рассчитываться кодом,
  а не приниматься из ответа модели.
- Вымышленные объекты и координаты MUST NOT подменять реальные данные.
- При сбое геосервиса система MUST отличать техническую ошибку источника от ситуации, когда
  подходящих объектов действительно нет, и сообщать пользователю разное.
- Изменение алгоритма подбора MUST сохранять проверки расстояний, лимитов и допустимого
  числа точек и сопровождаться тестами.

**Обоснование:** ценность продукта в том, что по маршруту можно реально пройти.

### III. ИИ под контролем кода

ИИ — вспомогательный компонент, а не единственная опора приложения.

- Провайдеры ИИ (Claude, DeepSeek) MUST подключаться через общий интерфейс; смена провайдера
  не требует изменений в бизнес-логике.
- Ответы моделей MUST валидироваться до использования.
- При недоступности ИИ MUST срабатывать предусмотренный резервный сценарий (эвристика или
  справочный текст), а пользователь MUST получать понятное уведомление.
- В режиме «Мифы и легенды» модель MUST опираться на переданные источники, а легенды MUST
  быть явно обозначены как легенды; выдумка под видом факта недопустима.
- Смена провайдера или состава передаваемых ему данных MUST отражаться в политике
  конфиденциальности.

**Обоснование:** модели ошибаются и бывают недоступны; продукт не должен ломаться и вводить
в заблуждение.

### IV. Источники, лицензии и атрибуция

У каждого рассказа и медиафайла MUST быть понятное происхождение.

- Допустимые источники сведений о местах: OpenStreetMap, Wikipedia, Wikidata, Wikimedia
  Commons; новый источник добавляется только с проверкой его лицензии.
- Для материалов Wikimedia MUST сохраняться и показываться автор, лицензия и ссылка на
  источник — в интерфейсе, экспорте и API.
- Изменения интерфейса, экспорта или API MUST NOT удалять атрибуцию.
- Сбой необязательного источника (например, фотографий) SHOULD NOT блокировать создание
  маршрута.

**Обоснование:** соблюдение лицензий — юридическое условие использования открытых данных.

### V. Безопасность и приватность по умолчанию

- Секреты (ключи ИИ, TTS, SMTP) MUST храниться в переменных окружения или защищённых
  настройках сервера и MUST NOT передаваться клиенту.
- Репозиторий публичный: файлы `.env`, базы данных, пользовательские загрузки и любые
  ключи MUST NOT попадать в git; перед публикацией изменений это проверяется.
- Пароли MUST храниться только в виде стойких хэшей; токены подтверждения почты и сброса
  пароля — только в виде хэшей.
- Доступ к приватным маршрутам и пользовательским материалам MUST проверяться на сервере.
- Входные данные и загружаемые файлы (размер, количество, MIME-тип) MUST валидироваться.
- Изменения авторизации, сессий, ролей и прав MUST сопровождаться негативными тестами.
- Персональные данные MUST передаваться внешним провайдерам только в объёме, необходимом
  для функции, и с раскрытием этого в политике конфиденциальности.

**Обоснование:** сервис хранит аккаунты и пользовательский контент; утечка необратима.

### VI. Надёжность и целостность данных

- Сервер MUST быть источником истины для бизнес-правил, прав доступа, лимитов и состояния
  маршрута.
- Изменения схемы SQLite MUST выполняться совместимыми миграциями, применяемыми при запуске.
- Обращения к внешним сетевым сервисам MUST иметь тайм-ауты, обработку ошибок и понятный
  пользователю резервный сценарий.
- Фоновые задачи MUST иметь наблюдаемый статус, корректно обрабатывать ошибки, продолжаться
  после перезапуска сервера и не создавать дубликатов там, где предусмотрена идемпотентность.
- Пользовательские данные MUST NOT удаляться или преобразовываться без явного требования и
  проверенного сценария миграции.

**Обоснование:** потеря маршрутов и рассказов пользователей — самый дорогой вид сбоя.

### VII. Проверяемое качество

- Клиент и сервер MUST быть написаны на TypeScript со строгой типизацией.
- Новая бизнес-логика SHOULD выноситься из UI и HTTP-обработчиков в тестируемые модули.
- Исправление дефекта MUST сопровождаться регрессионным тестом.
- Перед завершением задачи MUST быть запущены относящиеся к ней тесты и проверка типов;
  для изменений клиента — также lint.
- Задача MUST NOT объявляться завершённой, если необходимые проверки не запускались или
  упали; результат проверок фиксируется явно.

**Обоснование:** проект развивается с помощью ИИ-агентов; автоматические проверки —
главная защита от регрессий.

### VIII. Совместимость и минимальные изменения

- Действующие пользовательские сценарии, API-контракты и формат данных MUST сохраняться,
  если их изменение не является целью задачи.
- Изменения API MUST быть согласованы с клиентом и отражены в контрактах спецификации.
- Новые зависимости MAY добавляться только при обоснованной необходимости; для
  Expo/React Native MUST проверяться совместимость с используемой версией Expo SDK.
- Массовые рефакторинги, не связанные с задачей, MUST NOT выполняться без отдельного
  обоснования.

**Обоснование:** небольшие изменения легче проверить, откатить и выложить.

## Эксплуатация и production

- Production MUST работать по HTTPS за обратным прокси с корректной настройкой доверенного
  прокси (`TRUST_PROXY`).
- Публичные сервисы OpenStreetMap и связанные эндпоинты MUST NOT считаться гарантированно
  масштабируемой инфраструктурой; рост нагрузки требует собственного или платного решения.
- Сервер работает одним экземпляром с локальной SQLite и локальным хранилищем файлов;
  переход на несколько экземпляров MUST начинаться с решения по общей базе и хранилищу.
- Резервное копирование базы данных MUST выполняться автоматически, каждая копия MUST
  проверяться на целостность; процедура восстановления MUST быть документирована.
  Копирование загруженных файлов (аудио, фото) выполняется по решению владельца продукта.
- Выкладка MUST выполняться скриптом развёртывания, который запускает проверку типов и тесты
  до изменения сервера; перед изменениями схемы данных MUST делаться копия базы.
- Публичный пользовательский контент MUST иметь процесс жалоб и модерации, соответствующий
  правилам App Store и Google Play.

## Процесс разработки

- Новые функции SHOULD проходить цикл Spec Kit: `/speckit-specify` → `/speckit-clarify` →
  `/speckit-plan` → `/speckit-tasks` → `/speckit-analyze` → `/speckit-implement` →
  `/speckit-converge`.
- Спецификация описывает «что и зачем» без деталей реализации; план — «как» в рамках
  существующего стека (Fastify + SQLite на сервере, Expo/React Native в клиенте).
- Реализация MUST выполняться небольшими проверяемыми порциями в git; каждая порция
  завершается проверками из принципа VII.
- Спецификация базового состояния (`specs/001-baseline-project`) описывает существующий
  продукт и MUST NOT использоваться как задание на повторную реализацию.
- Решения, которые принимает владелец продукта, MUST оформляться как открытые вопросы,
  а не как принятые решения.

## Governance

- Конституция имеет приоритет над остальными практиками и документами проекта. План каждой
  функции MUST содержать проверку соответствия принципам (Constitution Check); отступление
  от принципа MUST быть обосновано в плане.
- Изменение конституции требует: описания причины; проверки влияния на спецификации, планы,
  задачи и шаблоны; обновления версии и Sync Impact Report; утверждения владельцем продукта.
- Версионирование — семантическое: MAJOR — удаление или несовместимое переопределение
  принципа; MINOR — новый принцип или раздел либо существенное расширение требований;
  PATCH — уточнения формулировок без изменения смысла.
- `/speckit-analyze` и ревью изменений MUST проверять соответствие конституции; нарушение
  MUST-правила блокирует завершение задачи.
- Оперативные сведения о разработке и развёртывании находятся в `README.md`.
